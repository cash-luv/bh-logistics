# 관리자 웹 프롬프트 모음 (관리자 0 ~ 12)

기사앱 프롬프트(0~9) 중 9번(관리자 웹 시작)은 이 문서가 대체합니다.
관리자 웹은 기사앱 폴더와 **별도 폴더**(`~/dev/bh_admin_web`)에서 만듭니다.

## 시작하기 전 준비 (한 번만)

1. **Node.js 설치**: nodejs.org에서 LTS 버전을 받아 설치합니다. 터미널에서 `node -v`를 입력해 숫자가 나오면 성공입니다.
2. **폴더 만들기**: 터미널에서 아래를 실행합니다.
```
mkdir -p ~/dev/bh_admin_web/docs
```
3. **파일 복사**
   - 이 묶음의 `bh_admin_web/AGENTS.md`를 `~/dev/bh_admin_web/`에 넣습니다.
   - 기사앱의 `docs/firestore_schema.md`를 `~/dev/bh_admin_web/docs/`에 복사해 넣습니다.
4. **Antigravity에서 열기**: File > Open Folder로 `~/dev/bh_admin_web`을 엽니다. 기사앱과는 **창을 따로** 쓰는 것이 헷갈리지 않습니다.
5. **Firebase 웹 앱 등록**은 관리자 1번에서 안내를 받으면서 합니다.

## 사용법

- 순서대로 **하나씩** 보냅니다. 한 번 보낼 때마다 브라우저에서 확인하고, 잘 되면 Source Control에서 Commit한 뒤 다음으로 넘어갑니다.
- 파일이 여러 개 바뀌는 프롬프트는 Antigravity의 **Planning 모드**로 보내세요.
- 에러가 나면 터미널이나 브라우저 콘솔의 메시지를 전부 붙여넣고 "원인을 쉬운 말로 설명하고 고쳐줘"라고 하면 됩니다.
- 관리자 웹을 켜는 명령어는 `npm run dev`이고, 브라우저에서 터미널에 나온 주소(보통 `http://localhost:5173`)를 엽니다.
- 대괄호 `【 】`는 내 상황에 맞게 바꿔서 보냅니다.

## 관리자 0. 프로젝트 이해시키기 (코드는 바꾸지 않음)

```

- AGENTS.md (이 웹 프로젝트의 작업 규칙)
- docs/firestore_schema.md (DB 설계. 기사앱과 똑같이 따라야 해)

코드는 아직 만들지 말고 아래만 답해줘.
1. 관리자 웹이 해야 할 일을 5줄로 요약
2. 왼쪽 사이드바 메뉴 구성 제안
3. DB 설계를 보고 관리자 웹을 만들 때 조심할 점 (예: 스냅샷, 배정 트랜잭션, 날짜 변환)
4. 첫 번째로 할 일

요구사항 요약:
- 종합 KPI 대시보드: 이달 총매출, 운행 중 차량 수, 공차 수, 정비 필요 알림
- 기사·노선 매출 관리: 다중 노선과 단가 설정, 출퇴근 기록과 단가를 맞춰 월 결산 자동 계산과 시각화
- 차량 종합 정보와 공차 관리: 제원, 누적 주행거리, 공차 여부, 수리 내역, 검사 기한 D-Day
- 엑셀 다운로드: 운행 / 차량 / 정산 데이터
```

## 관리자 1. 프로젝트 만들기 + Tailwind + Firebase 연결

```

## 관리자 2. 로그인 + 관리자 권한 + 사이드바 레이아웃

```
로그인과 기본 레이아웃을 만들어줘.

[준비 안내]
- 첫 관리자 계정을 만드는 방법을 콘솔 클릭 순서대로 알려줘: Authentication에서 이메일/비밀번호 사용자 추가, 그 uid로 Firestore의 Users/{uid} 문서를 직접 만들어 role: "admin", name, isActive: true를 넣는 법. 입력할 값 예시도 줘.

[만들 것]
1. 로그인 화면 (이메일, 비밀번호). 에러는 쉬운 한국어로 (예: 비밀번호가 틀렸어요).
2. 로그인 후 Users/{uid}.role이 "admin"이고 isActive가 true인 사람만 들어올 수 있게. 아니면 "관리자만 사용할 수 있어요" 안내 후 로그아웃.
3. 로그인 유지, 새로고침해도 로그인 상태 유지. 로그인 상태를 확인하는 동안에는 로딩 표시.
4. 보호된 라우팅 (로그인 안 하면 로그인 화면으로). React Router 사용.
5. 레이아웃: 왼쪽 사이드바(대시보드, 운행 기록, 차량, 기사, 노선, 월 결산)와 오른쪽 메인 영역. 맨 위에 로그인한 사람 이름과 로그아웃 버튼.
6. 각 메뉴는 아직 "준비 중" 화면으로 둬.

디자인: 깔끔한 흰색 바탕, 파랑 포인트(#1E5EFF), 사이드바는 짙은 남색. 지금 메뉴 위치가 어디인지 보이게 강조.
끝나면 바뀐 파일 목록과 화면에서 무엇이 보여야 하는지 알려줘.
```

## 관리자 6. 기사 ↔ 차량 배정

```
기사와 차량을 배정하는 기능을 만들어줘. 배정 정보는 두 곳에 있어서 반드시 같이 바뀌어야 해.
- Users/{기사}.assignedVehicleId
- Vehicles/{차량}.assignedDriverId, assignedDriverName

[만들 것]
1. 차량 목록의 각 행(또는 상세)에서 "배정 변경" 버튼 → 기사 선택 창(배정 가능한 활성 기사만, "공차로 만들기" 포함).
2. 배정은 Firestore 트랜잭션 하나로 처리해서 아래를 한꺼번에 수정:
   - 이 차량의 기존 기사 배정 해제
   - 새로 선택한 기사의 기존 차량 배정 해제
   - 새 기사 ↔ 이 차량 연결
3. 차량 status가 driving(운행 중)이면 배정을 바꾸지 못하게 막고 이유를 쉬운 말로 안내해줘.
4. 기사 목록의 배정 차량 칸과 차량 목록의 배정 기사 칸이 같이 갱신되는지 확인하는 방법을 알려줘.
5. 배정이 바뀌어도 이미 저장된 DailyLogs(과거 기록)는 바뀌면 안 돼. (그 기록들은 출근 시점의 이름/번호판 스냅샷이야.)

끝나면 확인 방법과, 트랜잭션이 중간에 실패해도 한쪽만 바뀌지 않는다는 점을 쉬운 말로 설명해줘.
```

끝나면 샘플 데이터가 없어도 0으로 잘 보이는지, 데이터를 넣으면 숫자가 어떻게 바뀌는지 확인하는 방법을 알려줘.

## 관리자 8. 운행 기록 (DailyLogs)

```
운행 기록 화면을 만들어줘. DailyLogs 문서 1개가 한 줄이야.

[목록]
- 위쪽 필터: 월(기본값 이번 달), 기사, 차량, 상태(in_progress / completed / void), "점검 이상만", "거리 이상만(kmCheck가 low 또는 high)", "퇴근 누락만(in_progress인데 오늘 이전 날짜)".
- 컬럼: 날짜, 기사, 차량번호, 노선, 단가, 출근 시각, 퇴근 시각(KST), 시작km, 종료km, 운행km, 점검 이상 표시, 거리 상태, 상태.
- 월 단위로만 조회하고(yearMonth), 한 번에 너무 많이 읽지 않게 페이지 나누기 또는 "더 보기".

[상세 (옆에서 열리는 패널)]
- 출근 사진 3장(외부, 내부, 계기판)과 퇴근 계기판 사진. Storage 경로로 getDownloadURL을 만들어 보여주고, 누르면 크게 보기.
- 점검 체크리스트(타이어 공기압, 요소수, 연료)의 정상 / 확인 필요.
- 출근 / 퇴근 특이사항 메모.
- 퇴근 위치: 위도·경도 숫자와 "지도에서 보기" 링크(https://www.google.com/maps?q=위도,경도 형식, API 키 필요 없는 방식).
- 위치 정확도가 낮으면(예: 100m 이상) 안내 표시.

[관리자 보정]
- 퇴근 누락 건: 종료 주행거리와 퇴근 시각을 관리자가 입력해서 completed로 바꾸고 운행km 자동 계산.
- 잘못 입력된 기록은 삭제하지 말고 void(무효) 처리. 사유 입력칸과 확인 창 필수. 무효 처리하면 매출 집계에서 빠진다는 점을 안내.
- 이 보정은 언제, 누가 했는지(adjustedBy, adjustedAt, adjustReason) 기록하자. 이건 스키마에 없는 필드니까 먼저 제안만 하고, 내가 OK하면 docs/firestore_schema.md에도 추가해줘.

끝나면 확인 방법을 알려줘.
```

## 관리자 9. 차량 상세 (공차, 검사, 정비)

```
차량 상세 화면을 만들어줘. 차량 목록에서 행을 누르면 열려.

[위쪽: 기본 정보 카드]
- 번호판, 제조사/모델/연식, 누적 주행거리(마지막 갱신 시각), 상태, 배정 기사(또는 공차), 검사 만료일과 D-Day, 마지막 검사일.
- 검사 완료 처리 버튼: 마지막 검사일을 입력하고 다음 만료일을 정하는 창.

[주차 위치 (공차일 때 특히 중요)]
- parking 정보: 장소 이름, 위치(지도에서 보기 링크), 사진(Storage 경로로 URL을 만들어 표시), 기록 시각과 기록한 사람.
- 없으면 "등록된 위치가 없어요".
- 관리자가 장소 이름을 직접 적어 넣는 입력도 제공.

[정비 이력 (Maintenance)]
- 탭 2개: "앞으로 할 정비(planned)"와 "수리 완료(done)".
- 각 항목: 분류, 제목, 날짜, 주행거리, 비용, 정비소, 누가 보고했는지(기사 보고는 표시), 출처(source).
- 정비 추가 창: 분류(엔진오일, 타이어, 브레이크, 요소수, 배터리, 검사, 기타), 제목, 날짜, 주행거리, 비용, 정비소, 다음 교체 주행거리(dueOdometerKm).
- planned → done으로 "완료 처리" 버튼 (완료일, 비용, 정비소 입력). 처리하면 Vehicles.openMaintenanceCount도 같이 줄이도록 WriteBatch로.
- 소모품 알림: dueOdometerKm까지 남은 거리가 1,000km 이하이면 주황색으로 표시.

[최근 운행]
- 이 차량의 최근 DailyLogs 10건 (날짜, 기사, 운행km).

끝나면 확인 방법을 알려줘.
```

## 관리자 10. 월 결산 + 시각화 + 마감

```
월 결산 화면을 만들어줘.

[계산]
- 월 선택 (기본값 이번 달, 한국 시간 기준).
- 그 달 DailyLogs 중 status가 in_progress 또는 completed인 문서를 기사별, 노선별로 묶어서 출근 일수 × 그날의 routePrice(스냅샷)를 더해. 단가가 중간에 바뀌었어도 각 날의 스냅샷 단가대로 합산돼야 해.
- 퇴근 누락(in_progress) 건수와 무효(void) 건수도 따로 알려줘. "퇴근 누락이 N건 있어요. 마감 전에 보정하세요."

[화면]
- 위쪽 카드: 월 총매출, 총 출근 일수, 총 운행 거리, 전월 대비 증감(%).
- 표: 기사별 행. 컬럼은 기사, 노선별 출근 일수와 금액, 합계 금액, 총 운행km. 맨 아래 합계 행.
- 차트(Recharts): (1) 기사별 매출 막대 차트 (2) 일별 매출 추이 선 차트 (3) 노선별 매출 비율 도넛 차트.
- 표의 기사를 누르면 그 기사의 그 달 운행 기록 목록으로 이동.

[마감]
- "이번 달 결산 마감" 버튼 → 확인 창 → Settlements/{yearMonth}_{driverId} 문서를 기사별로 저장(docs/firestore_schema.md의 Settlements 구조 그대로). status는 closed, closedAt, closedBy.
- 마감된 달은 화면에 "마감됨" 표시. 마감 후에 그 달 DailyLogs를 고치려고 하면 경고(관리자 8번의 보정 화면에서도 동일하게)를 보여줘.
- 마감된 달은 Settlements의 확정 금액을 보여주고, 현재 DailyLogs 합계와 다르면 "마감 이후 기록이 바뀌었어요"라고 알려줘.
- 마감 취소(draft로 되돌리기)는 확인 창을 한 번 더.

끝나면 확인 방법을 알려줘. 샘플 DailyLogs가 필요하니 콘솔에서 테스트 문서 몇 개를 넣는 방법과 예시 값도 같이 알려줘.
```

## 관리자 11. 엑셀 다운로드

```
엑셀 다운로드 기능을 만들어줘. ExcelJS를 쓰고, 브라우저에서 바로 만들어서 내려받게 해줘. (서버 없이)

## 관리자 12. 보안 점검 + 배포

```
관리자 웹을 마무리하고 배포하려고 해.

[보안 점검]
1. 지금까지 만든 모든 읽기/쓰기가 Firestore와 Storage 보안 규칙에서 막히지 않는지 점검해줘. 관리자는 전체 읽기/쓰기, 기사는 자기 것만이라는 원칙(docs/firestore_schema.md의 보안 규칙 방향)에 맞게, 관리자 웹에 필요한 규칙이 빠진 게 있으면 규칙 전체와 콘솔에 붙여넣는 방법을 알려줘.
2. 관리자가 아닌 사람이 로그인했을 때 어떤 데이터에도 접근하지 못하는지 내가 직접 해볼 수 있는 시나리오 5개.
3. .env, 서비스 계정 키 등 비밀 파일이 GitHub에 올라가지 않는지 점검.

[배포]
4. Firebase Hosting에 배포하는 방법을 단계별로. (firebase 로그인, hosting 초기화, 빌드 `npm run build`, 배포) 이 프로젝트가 단일 페이지 앱이라는 점도 설정해줘. 배포된 주소를 알려주는 확인 방법도.
5. Firebase 콘솔의 Authentication > 승인된 도메인에 배포 주소가 들어가 있는지 확인하는 방법.

[마무리]
6. 모든 화면에서 로딩 / 빈 상태 / 에러 상태가 잘 나오는지, 큰 목록에서 느리지 않은지 점검하고 고칠 곳을 알려줘.
7. README.md 초안: 프로젝트 소개, 주요 기능, 사용 기술, 실행 방법, 화면 설명 자리. 포트폴리오로 공개할 거라 실제 회사 정보나 개인정보는 넣지 마.
```

## 자주 쓰는 짧은 프롬프트

**에러가 났을 때**
```
에러가 났어. 원인을 쉬운 말로 먼저 설명하고 고칠 방법을 알려줘.
【터미널 또는 브라우저 콘솔 메시지 전체 붙여넣기】
```

**Firestore 인덱스 에러**
```
Firestore가 인덱스가 필요하다는 에러를 보여줬어. 쉬운 말로 설명하고, 에러 메시지의 링크로 인덱스를 만드는 방법을 단계별로 알려줘. 같은 인덱스를 firestore.indexes.json에 추가하는 방법도.
【에러 메시지 붙여넣기】
```

**화면 점검**
```
방금 만든 화면이 AGENTS.md의 규칙(한국어, 로딩/빈 상태/에러 상태, 금액·거리 표시, KST 변환, 위험 동작 확인 창)을 지키는지 점검하고, 어긴 곳을 고쳐줘.
```

**Firestore 읽기 비용 점검**
```
이 프로젝트에서 Firestore를 읽는 곳을 모두 찾아서, 컬렉션 전체를 읽거나 불필요하게 자주 읽는 곳이 있는지 알려줘. 월 단위나 limit으로 줄일 수 있는 곳을 고쳐줘.
```

**GitHub에 올리기 전 점검**
```
이 프로젝트를 GitHub에 올리려고 해. 비밀키, .env, 실제 기사 이름이나 전화번호 같은 개인정보가 코드나 문서에 들어 있는지 찾아서 알려줘. 올리면 안 되는 파일이 .gitignore에 빠져 있는지도 확인해줘.
```

**문서 갱신**
```
오늘 작업한 내용을 반영해서 docs/PROJECT_STATUS.md를 만들거나 갱신해줘. 완료한 것, 아직 안 한 것, 현재 폴더 구조, 알려진 문제를 적어줘.
```
